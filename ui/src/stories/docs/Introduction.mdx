# The core NUI shell

`core/ui` is the **only** user interface the players download. It is a Vue 3 + Vite app that
Vite builds into `core/html` (`assets/app.js`, `assets/app.css`, no hashes, so the manifest's
`files { 'html/**' }` stays stable), and `fxmanifest.lua` hands it to the CEF as
`ui_page 'html/index.html'`.

It is a **game overlay**: `html`, `body` and `.core-root` are transparent and
`pointer-events: none`. Nothing in it reacts to the mouse unless a modal or a plugin page is
open — otherwise the player could not shoot, drive or look around.

Because the CEF is composited above *everything* the game draws, the pause menu included, the
client also takes the whole shell away when the game needs the screen: `client/ui.lua` watches the
pause menu, screen fades, the player switch, warning screens and the cinematic camera
(`Config.UI.AutoHide`, one 200 ms thread) and sends `shell:visible` on each flip, which puts
`is-hidden` on `.core-root` (`visibility: hidden; pointer-events: none`). A plugin joins in with
`Core.UI.hide('cutscene')` / `Core.UI.show('cutscene')`, and the server with
`Core.UI.hide(src, 'cutscene')`. Hiding never unmounts anything — timers, the progress bar and the
HUD keep running underneath — but it *does* cancel an open modal, because nothing invisible may
keep NUI focus. See **Shell → Visibility** and DESIGN §31.

Every story in this Storybook drives the same reactive store the game drives, with the same
`SendNUIMessage` payloads. Nothing is faked with component props. The **Lua** panel
(bottom right, next to Controls and Interactions) shows, per story:

1. the `Core.UI.*` call a script would make,
2. the message(s) that call puts on the wire,
3. every NUI callback the shell posts back while you interact,
4. what the awaiting Lua call therefore returns.

## How Lua drives it

There are exactly two directions, both defined in DESIGN §6.10.

```
client/ui.lua  --  SendNUIMessage({ action = 'menu:open', ... })  -->  bridge.js 'message'
                                                                        |
                                                            store.js actions[action](msg)
                                                                        |
                                                                Vue components render
                                                                        |
                                             player presses Enter / clicks / Esc
                                                                        |
client/ui.lua  <--  fetch('https://core/menu_result', { id, value })  --  bridge.post()
                    RegisterNuiCallback resolves the pending promise
```

* **Lua → NUI** is `SendNUIMessage({ action = '<name>', ... })`. `src/bridge.js` dispatches the
  `window 'message'` event by `action` to the handlers `src/store.js` registered; the store is
  the single source of truth and the components are dumb renderers.
* **NUI → Lua** is `post(name, body)` → `fetch('https://<resource>/<name>')`, answered by a
  `RegisterNuiCallback`. The blocking helpers (`menu.open`, `input.open`, `alert`, `progress`)
  park a promise under a request `id` and resolve it when the matching callback arrives.

The shell is **optimistic**: `menuResult()` hides the menu and *then* posts, so the UI never
waits a frame for Lua. The `menu:close` Lua sends afterwards is a deliberate no-op.

Focus is Lua's job, not the page's: `client/ui.lua` calls `SetNuiFocus(true, true)` the moment
a page or a built-in modal (menu / input / alert) is open and `SetNuiFocus(false, false)` the
moment none is, with a 500 ms watchdog for the case where the page died with focus held.

## What lives where

| file | job |
| --- | --- |
| `src/main.ts` → `src/shell.ts` | the page entry and `createShell(target, opts?)` — the boot order the dev host and the tests reuse |
| `src/runtime/*.ts` | the platform (§38.6): `protocol`, `transport`, `scope`, `plugins`, `pages`, `layers`, `feeds`, `errors`, `host`, `inspector` |
| `src/bridge.js` | the legacy transport shim: `post()`, `onMessage()`, and the `window.__core.onPost` / `onMessage` taps this Storybook listens on |
| `src/store.js` | one `reactive()` state object + every `action` handler + the global keyboard rules |
| `src/coreui.js` | `window.CoreUI`, the legacy surface (§38.12) |
| `src/App.vue` | mounts the built-ins; no logic |
| `src/shell/*.vue` | render store state as kit compositions, own their local keyboard (Tab / Enter / arrows) |
| `sdk/` | the `@core/ui` package a plugin builds against (contract, facade, `coreUI()`, tokens, dev host) |

Keyboard ownership is split on purpose: **Escape** and the progress cancel keys
(`x` / `Backspace`) live in `store.handleKeydown` because they mean "cancel whatever is
topmost", while `↑ ↓ Enter Tab` live in the component that is on screen.

## One CEF page, many plugin frontends (DESIGN §38)

A plugin **owns** its frontend: it builds `<plugin>/ui/dist`, opts in with `core_ui 'ui/dist'`
plus `files { 'ui/dist/**' }`, and core imports the module at runtime from that resource's own
origin (`https://cfx-nui-<resource>/ui/dist/plugin.<hash>.js`). One CEF page, one Vue (core's,
handed over through a host object), one kit, one focus owner — but changing a page means
`npm run build` in that plugin and `restart <plugin>`, never a core rebuild. See
**Docs → UI Platform**.

```lua
-- the plugin's client script stays the authority on id, type and owner
Core.UI.registerPage('bank', { type = 'page', keepInput = false })
Core.UI.open('bank', { balance = 182450 })
```

```ts
// <plugin>/ui/src/index.ts — built by coreUI(), imported by core at runtime
import { defineUIPlugin, definePage } from '@core/ui'
import Page from './Page.vue'
export default defineUIPlugin({ pages: { bank: definePage({ component: Page }) } })
```

Besides the page plumbing, `window.CoreUI` hands a page the shell's own live data —
`hud` (money, name, server id and faction plus the live feed: health / armour / speed / street /
zone / voice), `state`, `stats`, `minimap`, `lang` / `t(key, vars)` for core's strings and
`playSound(name, set)` — all readonly and reactive, so a page never has to ask Lua for something
the shell already knows. Core itself only *draws* the §39 vitals strip out of that; money,
identity, faction and location are there for a plugin to render.

The SDK a plugin builds against is the npm workspace package `@core/ui` (`core/ui/sdk`): the
typed host contract, a facade under 2 KB, the `coreUI()` Vite plugin and core's tokens. Dev
dependencies are still hoisted by the workspace at `resources/package.json` (`core/ui`,
`core/ui/sdk`, `*/ui`), so a plugin that needs an extra runtime library adds it to its own
`ui/package.json` and `npm install` at `resources/` hoists it — but it is bundled into **that
plugin's** dist, not into core's. The `script` / `style` URL loader is gone; see
**Docs → Plugin Pages**.

## Styling (Tailwind v4)

`src/styles.css` is the single stylesheet: `@import "tailwindcss"`, one `@theme` block of design
tokens, and the shared `.core-*` component classes. No `tailwind.config.js`, no PostCSS — the
CSS *is* the config, compiled by `@tailwindcss/vite`. Because the tokens live in `@theme`, each one
is also a utility (opacity modifiers included, e.g. `bg-accent/10`):

| group | utilities |
| --- | --- |
| surfaces | `bg-panel` `bg-panel-solid` `bg-panel-raise` `bg-backdrop` |
| hairlines | `border-border` `border-border-strong` |
| text | `text-fg` `text-fg-dim` `text-fg-faint` |
| accent / states | `text-accent` `bg-accent-soft` · `text-success` `text-error` `text-warning` `text-info` |
| shape | `rounded-ui` `rounded-ui-sm` `shadow-ui` `ease-ui` |
| type | `font-sans` `font-mono` · `text-ui` `text-ui-sm` `text-ui-xs` |
| motion | `animate-core-slide-in` `animate-core-fade-in` `animate-core-pop-in` |

The component classes are what the built-ins are made of, and any page can reuse them:
`core-panel` `core-modal` `core-backdrop` `core-title` `core-text` `core-label` `core-btn`
(`--primary` / `--ghost` / `--danger`) `core-field` `core-input` `core-select` `core-check`
`core-key` `core-list` `core-item` (`.is-active` / `.is-disabled`) and `core-interactive`
(`pointer-events: auto` — the shell is click-through, so anything clickable needs it).

```vue
<div class="core-panel core-interactive w-[380px] font-sans text-fg">
  <h1 class="core-title">my_plugin</h1>
  <p class="text-ui-sm text-fg-dim">Utilities + tokens, no stylesheet of your own.</p>
  <button class="core-btn core-btn--primary mt-3" @click="close()">Close</button>
</div>
```

The tokens live in `ui/sdk/theme.css` (nothing but `@theme static` blocks — Tailwind refuses
`theme(reference)` on anything else); core's `styles.css` imports it, and a plugin build
references the same file, so a plugin's sheet carries only the utilities *it* uses. Core's entry
is `@import "tailwindcss" source(none)` plus explicit `@source` lines, because Tailwind's
automatic detection walks up to the workspace root and would compile plugin utilities back into
core. A scoped `<style>` that uses `@apply` points Tailwind at the theme by package specifier:
`@reference "@core/ui/reference.css";`. It reads the tokens and emits nothing.

**Never filter the backdrop** — neither the CSS property nor Tailwind's `backdrop-` utilities. The
game frame is not part of the CEF's compositing surface, so FiveM paints the filtered area as a solid
black box — it looks fine in this Storybook and black in-game. Put `data-core-blur` on the panel
instead.

(The literal property name is spelled out in core's README, not here: this file is inside `ui/src`,
so Tailwind scans it and would emit the matching — dead — utility into the shipped bundle.)

## Game blur (DESIGN §32)

A CSS filter cannot see the game, but FiveM's NUI core can: it hooks `glTexParameterf` and binds
the game's back buffer to a WebGL texture, which is how the FiveM main menu draws its own blurred
background. `src/gameblur.js` does the same — one hidden source canvas holding the current frame at
`Config.UI.Blur.Fps` (30) and `Scale` (0.5), and for every element carrying `data-core-blur` a
`.core-glass` wrapper behind it (`z-index: -1`) whose canvas is a blurred crop of that source, tinted
with `--core-glass-tint` so the panel keeps its own colour. A plugin page needs no JavaScript: the
attribute is the whole API (`data-core-blur="18"` for a custom radius, `"0"` to opt out). It costs
one small canvas copy per consumer per frame, so consumers are **panels, never list rows** — the
shell's own built-ins keep the count at 12 or fewer (the §39 vitals strip is not one of them: its
plates are opaque). Outside the CEF there is no hook, so the module probes once and falls back to
a procedural gradient (`<html data-game-blur="fallback">`),
which is what every story in this Storybook shows. See **Shell → Game blur**.

## Working offline

`window.GetParentResourceName` only exists inside the CEF. Without it the shell switches to
dev mode: `post()` logs instead of fetching, and `window.__core.send({ action: … })` fakes an
incoming message. That is how `core/ui/tests/shell-regression.js` drives `html/index.html`
under `agent-browser`, and it is exactly what the `send()` helper in these stories uses.
